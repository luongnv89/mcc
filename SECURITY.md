# Security Policy

## Supported versions

mcc is pre-1.0 (currently 0.13.0). Security fixes are made on `main` and shipped in the next release; only the latest release and `main` are supported.

| Version | Supported |
|---|---|
| latest release / `main` | yes |
| older releases | no |

## Reporting a vulnerability

**Please do not open a public GitHub issue, discussion or pull request for a security vulnerability.**

Report it privately instead:

1. **Preferred:** use GitHub private vulnerability reporting at <https://github.com/luongnv89/mcc/security/advisories/new>.
2. **Alternatively:** email the maintainer at contact@luongnv.com with the subject prefix `[mcc security]`.

### What to include

- A description of the vulnerability and its impact
- The mcc version (`mcc --version`) or commit, your OS and your shell
- Step-by-step instructions to reproduce it, or a proof of concept
- The affected command, file or source location, if you know it
- Any suggested fix or mitigation

Never include a real access token or credentials in your report. Use placeholder values.

### What to expect

mcc is maintained by volunteers, so responses are best effort:

- An acknowledgment within about 7 days
- An assessment and, if the report is confirmed, a plan for a fix
- A fix released as soon as practical, with credit in the advisory if you want it

Please give us a reasonable amount of time to fix the issue before you disclose it publicly.

## Scope

mcc manages Claude Code profiles on your machine, so it handles sensitive local data:

- **Credentials.** By default mcc reads no token: the usage in `mcc list`, `mcc usage` and `mcc run` comes from the rate limits the opt-in `mcc statusline` shim caches in `~/.mcc/state/<profile>/usage.json` from what Claude Code passes it. To warn before a login runs out, `mcc usage` reads one timestamp from each profile's `<config dir>/.credentials.json`, the login deadline (`refreshTokenExpiresAt`), into a structure that has no token field, and sends nothing over the network; it reads that deadline from the macOS Keychain only with `live = true` or `--all` (below), and reads nothing with `MCC_NO_USAGE` set. `mcc login PROFILE` (alias `mcc renew`), which you run to renew a login, reads the same deadline from the file and, on macOS, the Keychain (whatever `MCC_NO_USAGE` says) before and after it renews the login, and with `--refresh-only` also the access token's expiry (`expiresAt`): timestamps only, never a token. Only with `live = true` under `[usage]` in `~/.mcc/config.toml` (off by default), or for one run of `mcc usage --all` (every profile, the default included; it prints a risk notice each time), does mcc read each profile's Claude Code OAuth access token, from `<config dir>/.credentials.json` or, on macOS, from the login Keychain item Claude Code created for that config dir: with `live = true`, for the usage in those commands and in `mcc doctor` to check whether it has expired; with `--all`, for that one `mcc usage` run, which saves only the percentages and reset times it finds (never the token) to that same `usage.json` cache. The access token is kept in memory only, is never printed, logged or written anywhere, and is sent only to Anthropic's usage endpoint (`https://api.anthropic.com/api/oauth/usage`) for its own profile, or to the `MCC_USAGE_URL` test override (accepted only for `https://` URLs or `http://` on loopback), with no redirects followed and no proxy taken from the environment. mcc itself never refreshes a token (it never sends a refresh token or calls the OAuth endpoint): to renew a login, `mcc login` runs `claude auth login` for the profile, and `mcc login --refresh-only` runs one isolated `claude -p` request (haiku, one turn, no tools, MCP servers or hooks, only the user's own settings, in an empty directory, with credential variables removed, stopped after 2 minutes) so that Claude Code refreshes its own token. `mcc usage --all` makes the same request, announced on stderr first, for each account whose access token it finds expired: in the first existing project mapped to that profile with `mcc project set`, where Claude Code sees the project's git status and `CLAUDE.md` as in any session there, or, for a profile no project maps to, in a new empty folder. It starts none for a profile whose login has passed its deadline or whose refresh failed in the last 30 minutes, and spends at most 3 minutes on refreshes per run. Both commands hold `~/.mcc/state/<profile>/refresh.lock` while the request runs, so two never refresh one profile at once.
- **Devin's login.** When the Devin CLI is signed in, `mcc list`, `mcc usage` and bare `mcc` show Devin's usage beside your profiles. By default mcc only checks that Devin's credentials file exists (`$XDG_DATA_HOME/devin/credentials.toml`, else `~/.local/share/devin/credentials.toml`), reads no token, and shows the numbers the last lookup saved. Only with `live = true` under `[usage]` (after a one-time note, recorded as `devin_disclosed_at`) or for one run of `mcc usage --all` (whose notice then names Devin's API), never with `MCC_NO_USAGE` set and never for bare `mcc`, does mcc read the session token from that file (re-read each time, kept in memory only, never printed, logged or written anywhere) and send it to Devin's API (`https://app.devin.ai/api`: `/organizations`, then `/<org>/billing/quota/usage`), or to the `MCC_DEVIN_API_URL` test override (accepted only for `https://` URLs or `http://` on loopback), with no redirects followed and no proxy taken from the environment. With `live = true`, `mcc doctor` also checks whether that file holds a token, without showing it. mcc never signs Devin in and never moves, copies or writes Devin's credentials file, its configuration (`~/.config/devin`) or `~/.local/bin/devin`; `mcc devin` starts the Devin CLI with your arguments and an unchanged environment.
- **API-key profiles.** `mcc add` with `--api-key-stdin` (a pipe) or `--api-key-prompt` (hidden, at a terminal) writes the Anthropic API key once to a `0600` file in `~/.mcc/keys` (a `0700` directory, the file created with `O_EXCL` and renamed into place), named after the profile's directory, and sets the profile's `apiKeyHelper` to `cat` that file. mcc never reads it again: Claude Code does, when it needs the key. With `--api-key-helper CMD`, Claude Code runs your command and mcc stores nothing, and never runs or prints the command. A key is never accepted as an argument: anything containing `sk-ant-` is refused as an alias and redacted from the command line mcc logs and from argument-parsing errors (other commands' errors may still repeat a mistyped value, so never paste a key as an argument). The profile's launcher, `mcc run`, `mcc exec` and `mcc env` unset `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`, so a key in your shell can't replace the profile's. `mcc login`, `mcc default` and the token refresh of `mcc usage --all` leave these profiles alone, and `mcc delete` removes the key file mcc wrote (`--keep-auth` keeps it), never a helper's own.
- **Your other machines.** Only when you list machines under `[machines.NAME]` in `~/.mcc/config.toml` does mcc connect anywhere over SSH, and only to those hosts, for two commands: `mcc usage` and `mcc remote`. For `mcc usage`, it runs `ssh -o BatchMode=yes -o ConnectTimeout=10 -- HOST` with your own SSH keys and configuration (mcc never reads `~/.ssh/config` itself), and the command it runs there is `mcc usage`, with every word single-quoted. No login or token crosses between machines: each machine looks up its own accounts with its own login, and `mcc usage --all` asks another machine to look up only the accounts this machine doesn't have (`mcc usage --all --only PROFILES` there), with that machine's own token. What comes back is that machine's usage table, with each account as a SHA-256 of its email and organization ID (a pseudonym, not a secret: emails never cross). mcc checks a reply before using it (at most 4 MiB, schema 2, profile names re-checked, times more than a minute ahead of this clock ignored) and saves only newer numbers for an account this machine also has, to `~/.mcc/state/<profile>/usage.json`. `mcc config edit` refuses a host that starts with `-` or holds a space or control character, and `mcc config set` never sets machines. The first `mcc usage` that reads other machines explains this on stderr once (recorded as `machines_disclosed_at`).
- **Tasks on another machine (`mcc remote`).** `mcc remote PROFILE MACHINE TASK` runs Claude Code on this machine, as the profile, in headless mode (`claude -p`), and lets it run commands on the machine over SSH. mcc sends no login or token to the machine. The layers: Claude Code gets no built-in tools (`--tools ""`), only mcc's own MCP server (`--strict-mcp-config --mcp-config`), only that server's `run` tool allowed (`--allowedTools mcp__mcc-remote__run`) with every other call denied without a prompt (`--permission-mode dontAsk --permission-prompts none`), only the user's settings (`--setting-sources user`), hooks off and no saved session; it starts from a new `0700` folder under `~/.mcc/state/remote/` (its MCP config `0600`), removed on every way out, without the credential variables mcc strips from every child or `CLAUDE_CODE_ENABLE_CFC`, and gets the task on stdin, never as an argument. The `run` tool starts no shell here: it runs `ssh -n -o BatchMode=yes -o ConnectTimeout=10 -o ForwardAgent=no -o ForwardX11=no -o ForwardX11Trusted=no -o ClearAllForwardings=yes -o GSSAPIDelegateCredentials=no -o PermitLocalCommand=no -o RequestTTY=no -o ControlMaster=no -o ControlPath=none -o RemoteCommand=none -- HOST COMMAND`, the command as one argument, with only `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_*`, `TMPDIR`, `XDG_RUNTIME_DIR`, `KRB5CCNAME` and `SSH_*` (not `SSH_ASKPASS*`) in its environment; the host must be plain letters, digits and `._@:-`, checked by `mcc remote` and again by the tool. Outputs are cut at 256 KiB each and commands stopped after 10 minutes. mcc first checks the host with `true` the same way, and starts nothing if that fails. `--timeout`, Ctrl+C, SIGTERM, SIGHUP and SIGQUIT stop Claude Code's whole process group (SIGTERM, then SIGKILL); Ctrl+Z stops that group (SIGSTOP) before mcc stops, and continues it when mcc is continued, so nothing it started runs here unsupervised. mcc.log records the profile, the machine and how the run ended, never the task, Claude's report or a refused call, and the tool records only each command's exit status, duration and whether it timed out. Residual risks: commands run with your SSH key as the remote user, so they can do whatever that user can; whatever Claude knows (the task, the profile's `CLAUDE.md`, earlier output) can reach the machine in a command; output from the machine can steer Claude (prompt injection), including toward commands you didn't intend there; a command may keep running on the machine after a timeout or an interrupt, since stopping ssh doesn't stop it there; and it is Claude Code's permission system that denies every tool but `run`, so a Claude Code mod that approves calls, or a change in how Claude Code treats these flags, would change that. Every run prints a note saying so on stderr.
- **Files it writes.** Profile directories under `~/.mcc/profiles/`, launchers in `~/.local/bin/`, a managed alias block in your shell rc file, and its own state, logs and backups under `~/.mcc/`. With auto sync (`[sync] auto`, on by default), starting a profile from its launcher (which calls the hidden `mcc launch-sync <alias>`) or with `mcc run` writes to profiles without any other command: mcc copies what the default profile added or updated into that profile and the others the default changed for, after backing up what it replaces to `<profile>/.mcc-backup/<timestamp>-auto/` (it keeps the 10 latest of these per profile and removes older ones; backups of `mcc sync` and `mcc link` are never removed), and records each profile's state in `~/.mcc/state/<alias>/auto-sync.json`. For a profile that opts in to session sharing (`mcc share`), mcc moves its session transcripts into its group's store, `~/.mcc/shared/projects` or `~/.mcc/shared/groups/<name>/projects`, and replaces its `projects/` directory with a link there. `mcc statusline install` and `uninstall` (opt-in) change the `statusLine` in your default profile's `~/.claude/settings.json` (or the file it links to), after copying it to `~/.mcc/backups/`. `mcc login --refresh-only`, and `mcc usage --all` when it refreshes the token of a profile no project maps to, also create an empty, private folder (mode 0700) in the system's temporary directory for the one `claude -p` request and remove it when the request ends. Both write the lock file `~/.mcc/state/<profile>/refresh.lock`, and `mcc usage --all` records a failed refresh's time in `~/.mcc/state/<profile>/refresh-failed-at` (removed by a refresh that works). `mcc sync` (never auto sync) takes a settings key changed in any profile into the default's `~/.claude/settings.json`, after backing it up to `~/.claude/.mcc-backup/<timestamp>/`. Sync never copies an account-bound key (`apiKeyHelper`, `env.ANTHROPIC_API_KEY`, `env.ANTHROPIC_BASE_URL`, cloud-provider credentials and endpoints, `[sync] account_keys`) between profiles, copies a shared secret (a password, token or other secret it detects, or `[sync] secret_keys`) only after you agree at a prompt that names the key but never shows its value (`--yes` never agrees; without a terminal it is skipped; one you agree to take from a profile then reaches every profile without another prompt), and keeps values out of its output, `mcc diff` and `mcc.log`. An API-key profile's statusline keeps each session's estimated cost in `~/.mcc/state/<profile>/cost/<session_id>.json`. A successful live Devin usage lookup saves Devin's quota numbers and organization (never its token) to `~/.mcc/providers/devin/quota.json`.
- **Switching the default profile's account.** `mcc default PROFILE` and `mcc default --new`, which you run and confirm, change the account `~/.claude` (and, in a trade, PROFILE) is signed in to by running Claude Code's own `claude auth logout` and `claude auth login` for it, with the credential variables (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`…) removed. mcc never reads, copies or moves a credential itself: it checks each sign-in with `claude auth status` before the next step, holds `~/.mcc/state/<profile>/refresh.lock` for each profile it signs out and in, forgets their cached `usage.json` and `refresh-failed-at`, records the new account in `~/.mcc/config.toml`, and sets `hasCompletedOnboarding` in Claude Code's `.claude.json` for that profile when the sign-in left it unset. Plain `mcc default`, and `mcc add` when `~/.claude` is missing, only run `claude auth status`, the same way. After an upgrade from mcc 0.7.0–0.9.x, the next mcc command removes the `claude` function an older `mcc default PROFILE` wrote to your rc file (between `# >>> mcc:default >>>` and `# <<< mcc:default <<<`, after backing the file up to `~/.mcc/backups/`) and `default_profile` from `~/.mcc/config.toml`.

Examples of issues that are in scope:

- Leaking an access token, an API key or a synced secret's value (to logs, output, files, or any host other than the ones above)
- Path traversal or writes outside the intended locations through profile aliases, sync paths or config values
- `mcc sync` copying an account-bound setting between profiles, or a shared secret you never agreed to
- Unsafe file permissions on files that hold credentials or account data
- Shell injection through the rc file alias block, the generated launchers or the command mcc runs on another machine over SSH (for `mcc remote`, a command reaching anything but the remote user's shell, or anything running on this machine)
- Deleting or overwriting files mcc did not create
- The install script installing a binary that doesn't match its release's SHA-256 checksum, downloading over anything but HTTPS, or building a directory that isn't its own clone

Out of scope: vulnerabilities in Claude Code itself or in Anthropic's services (report those to Anthropic), in the Devin CLI or Devin's services (report those to Devin's maintainers), and issues that require an attacker who already controls your user account.
