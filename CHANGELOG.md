# Changelog

All notable changes to mcc are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and mcc uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The same history is published at <https://luongnv89.github.io/mcc/changelog.html>.

## [Unreleased]

### Added

- `mcc remote PROFILE MACHINE TASK` has a profile do a task on one of your `[machines]` over SSH, on a machine that needs only sshd and a shell (no Claude Code, no mcc). Claude Code runs on this machine as the profile, in headless mode (`claude -p`), with no tools of its own and one MCP tool served by mcc (`mcc remote-tool`, hidden), which runs one command on the machine through a fixed, hardened `ssh` argument list (no agent, X11 or port forwarding, no Kerberos credential delegation). mcc checks the machine first (`ssh HOST true`), sends no login or token anywhere, gives the task on stdin and keeps it out of mcc.log, prints Claude's report on stdout (`--json`: the whole result) and a summary on stderr (how it ended, turns, cost, commands run and failed, refused tool calls), and exits 0 when Claude Code's run finished without an error (whether the task itself succeeded is for Claude's report to say). `--task-file PATH` or `-` (stdin) give the task, `--max-turns N` (30) and `--timeout SECS` bound the run; `--timeout`, Ctrl+C, SIGTERM, SIGHUP and SIGQUIT stop Claude Code and every ssh it started (exit 124, 130, 143, 129, 131); Ctrl+Z suspends them with mcc, `fg` resumes them, and the time suspended doesn't count against `--timeout`. Every run prints a note on stderr about what can reach the machine. ([#142](https://github.com/luongnv89/mcc/issues/142))
- `remote` and `remote-tool` are reserved profile names.

## [0.12.0] - 2026-11-24

mcc can now add Claude Code profiles that use an Anthropic API key instead of a Claude login: `mcc add ALIAS --api-key-stdin`, `--api-key-prompt` or `--api-key-helper CMD`. mcc never takes the key as an argument, and `mcc list`, `mcc` and `mcc usage` show these profiles in their own `API KEY` block with the estimated spend this month and an optional budget. `mcc usage` can also show the accounts on your other machines: name them under `[machines.NAME]` with `mcc config edit`, and mcc reads each one over SSH and prints a table per machine, where an account found on several machines shows its newest numbers. `mcc sync` now syncs `settings.json` key by key, so a setting changed in any profile reaches the default and every other profile; it asks before copying a shared secret, without ever showing the value, and never copies account-bound keys such as `ANTHROPIC_API_KEY`. mcc also warns about a setting it doesn't know in `~/.mcc/config.toml`, and `mcc sync` no longer mistakes a hook that runs `date -u` after `curl` for a secret.

### Added

- API-key profiles: `mcc add ALIAS --api-key-stdin`, `--api-key-prompt` or `--api-key-helper CMD` adds a Claude Code profile that uses an Anthropic API key (API usage billing) instead of a Claude login, through Claude Code's `apiKeyHelper` in the profile's `settings.json`. With `--api-key-helper` Claude Code runs your command and mcc stores nothing; with the other two, mcc writes the key once to a `0600` file in `~/.mcc/keys` and never reads it again. A key is never taken as an argument: anything containing `sk-ant-` is refused as an alias and redacted from the command line mcc logs and from argument-parsing errors (other commands' errors may still repeat a mistyped value, so never paste a key as an argument). The profile skips the sign-in, starts without your shell's `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`, and gets the mcc statusline in its settings overlay, which records each session's cost. `mcc list`, `mcc usage` and bare `mcc` show API-key profiles in their own `API KEY` block, without 5-hour or weekly windows, with the estimated spend this month on this machine and the budget set with `--budget` (or `mcc config set profiles.ALIAS.api_budget_usd`). `--json` and `--json-v2` add `auth: "api_key"`, `usage.est_cost_usd` and `usage.budget_usd`, and keep the old status and reason codes. `mcc login`, `mcc default` and the token refresh of `mcc usage --all` leave them alone, and `mcc delete` also removes the key file mcc wrote. What can and can't be tracked is in [docs/api-key-profiles.md](docs/api-key-profiles.md). ([#132](https://github.com/luongnv89/mcc/issues/132))
- `mcc usage` shows the accounts on your other machines next to this one's. Add a machine with `mcc config edit` as `[machines.NAME]` with `host = "…"` (what `ssh` connects to) and, when a non-interactive SSH session doesn't find mcc there, `mcc = "/full/path/to/mcc"`. `mcc usage` then runs `mcc usage` on each over SSH (`ssh -o BatchMode=yes -o ConnectTimeout=10 -- HOST …`, your own keys and SSH config; mcc never reads `~/.ssh/config`) and prints one table per machine after this one's (`local`), each under a `── name · updated … ───` rule as wide as the tables that names the machine and says when its numbers were last updated, or `updated —` and why it couldn't be read; a machine that fails never fails the command. An account on several machines is matched by a SHA-256 of its email and organization (the email never leaves its machine, and a personal plan and a work seat on one email stay apart): ALSO ON names the other machines it is on, every row of it shows its newest numbers from any machine, and this machine saves them to its cache when they are newer, so `mcc list`, `mcc run` and the status line show them too. `mcc usage --all` refreshes every machine with one live lookup per account: here for this machine's accounts, else on one machine that has the account, and its notice gains a line saying so. The first `mcc usage` that reads other machines explains this once on stderr (`[usage] machines_disclosed_at`). `mcc config edit` refuses a `[machines.NAME]` whose host starts with `-` or holds a space or control character, or whose `mcc` starts with `~`. Each machine needs this version of mcc or newer. Without `[machines]`, nothing changes. ([#130](https://github.com/luongnv89/mcc/issues/130))
- `mcc usage --json-v2` gains, when machines are set up, `updated_at` (this machine's own last update, from its own numbers) and a `machines` key after `profiles`: `[{"name", "host", "updated_at", "error", "profiles": [...]}]`, `error` being a code (`unreachable`, `timed_out`, `mcc_not_found`, `outdated`, `incompatible`, `failed`, `no_ssh`, `invalid_config`) or null; each profile row then also has `account_id` (the SHA-256 of its email and organization) and `also_on`. Schema 2 only gains keys; `--json` (schema 1), `mcc usage PROFILE` and `MCC_NO_USAGE=1` read this machine alone, as before. The Herdr plugin needs an update to show the new keys. ([#130](https://github.com/luongnv89/mcc/issues/130))
- `mcc usage --all --only PROFILES` looks up (and refreshes) only those profiles of this machine (comma-separated, `default` for `~/.claude`) and shows only them; it is how one machine asks another for an account's numbers. ([#130](https://github.com/luongnv89/mcc/issues/130))
- A setting mcc doesn't know in `~/.mcc/config.toml` (a misspelled `[machine.lab]` for `[machines.lab]`, say) is no longer ignored without a word: every command except the launch ones (`mcc run`, `mcc env`, `mcc exec`, `mcc devin`, the share hook) warns about it on stderr, with a "did you mean" for a near-miss top-level key, and says that mcc drops it the next time it saves the file. `mcc config edit` warns once it saves. `--json` output is unchanged. ([#130](https://github.com/luongnv89/mcc/issues/130))

### Changed

- `mcc sync` syncs `settings.json` key by key, with each `env` variable on its own, instead of as one file. It first reads the settings of every profile, whichever ones it syncs, and takes a key changed in one of them into the default's `settings.json` (backed up to `~/.claude/.mcc-backup/<timestamp>/`, written through a symlink), so a setting such as `env.CLAUDE_CODE_EXPERIMENTAL_CODE_MODE` turned on in one profile reaches every profile. Each key falls in a category: **basic** keys are synced; **shared secrets** (an `env` name containing `PASSWORD`, `SECRET`, `WEBHOOK`, …, with `API_KEY`, `TOKEN`, `PASS`, `PWD`, `DSN`, … as a part, or ending in `_KEY`; an `env` value with 32+ hex digits; a token-shaped value, a webhook's token in a URL included; a URL with a password; a webhook URL or one with a key-, token- or password-named query parameter, however short its token; an HTTP auth header, `Bearer` credential or `curl -u user:pass` in a command, or a command setting a secret-named variable (`PGPASSWORD=… psql`), unless it names a shell variable; `PASSPHRASE` and `HEADERS` (`OTEL_EXPORTER_OTLP_HEADERS`) names; detection is best-effort, and `[sync] secret_keys` / `account_keys` mark what it misses; or `[sync] secret_keys`) are taken from a profile, or copied from the default into a profile, only after a prompt that shows the key and where it comes from, never the value (`--yes` never agrees; without a terminal they are skipped, and auto sync leaves them to `mcc sync`; a declined value is not asked about again until it changes; one agreed to from a profile reaches every profile without another prompt); **account-bound** keys (`env.ANTHROPIC_API_KEY`, `env.ANTHROPIC_BASE_URL` and the other variables mcc strips from Claude Code, the Bedrock, Vertex and Foundry credentials and endpoints such as `env.AWS_BEARER_TOKEN_BEDROCK`, `env.AWS_SECRET_ACCESS_KEY` or `env.ANTHROPIC_VERTEX_BASE_URL`, `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `forceLoginMethod`, `forceLoginOrgUUID`, or `[sync] account_keys`) are never copied, added or removed. Each such key, and each key the default gives a profile, is reported with its category, source (a profile, or the default) and outcome (synced, asked, declined, skipped, conflict, removed); values never appear in the output, `mcc diff` (`<hidden>`) or `mcc.log`. A key changed differently in two places is a conflict, reported with how to settle it (`--force` gives the profile the default's value, or removes the key from the profile when the default dropped it); a key removed in a profile leaves the default only once you confirm it at a terminal (`--yes` never does, and without a terminal it is skipped; a declined removal is not asked about again while the default keeps that value), and a profile whose `settings.json` is missing, not a JSON object, or a symlink to the default's is never read for changes, and one with no keys of its own is never read for removals, so it can't empty the default; a `settings.json` mcc wrote and the profile deleted stays deleted as a local edit until `mcc sync ALIAS --force` restores it. ([#129](https://github.com/luongnv89/mcc/issues/129))
- A profile with settings of its own (its own `ANTHROPIC_BASE_URL`, say) no longer stops getting the default's new settings: sync and auto sync merge the default's keys in and keep the profile's. The default's account-bound keys no longer reach a profile on `add --clone`, `sync` or auto sync, and a profile's `settings.json` is now always written as a file, also when the default's is a symlink and the profile has no overlay. Auto sync never takes settings from a profile or writes the default's `settings.json`. Sync records from an older mcc are read as before and become per key on the next sync. When the default changed since such a record, a key only an edited profile has (new there, or dropped by the default?) is taken into the default only once you confirm it at a terminal (`skipped (needs confirmation)` with `--yes` or without one; a declined value is not asked about again until it changes), and a key both have with different values is a conflict, so a stale value never reverts the default; a key such a profile lacks is never proposed for removal. When several such profiles each changed a key, every change reaches every profile: the profiles' records are made per key before the default is written, so their reading doesn't change with it. A default `settings.json` or `settings.local.json` that isn't valid JSON is no longer copied byte for byte (its account-bound keys could reach every profile): `mcc sync` warns and leaves the profile's file as it is, auto sync too. `settings.local.json` is still synced as a whole file, but without the default's account-bound keys, keeping the profile's own, with a shared secret the default's adds or changes asked about per profile as in `settings.json` (`env.NAME in settings.local.json`), and with secret values hidden in `mcc diff`. `mcc add --clone` asks the same way before copying a shared secret of the default; without a terminal, or with `--yes`, it leaves it out and says `mcc sync ALIAS` will offer it. A segment of a file path in a settings value (such as Claude Code's project folder names, long mixed-case runs) is no longer mistaken for a token; one of a URL still is. A profile `settings.json` that isn't a JSON object, overwritten whole by `--force`, gets the default's shared secrets only once you agree, as above. A profile's settings file left by an older mcc as a symlink to the default's is replaced by a file without the default's account-bound keys. ([#129](https://github.com/luongnv89/mcc/issues/129))

### Fixed

- `mcc sync` no longer holds a hook or status line as a shared secret when a `date -u` follows a `curl` in the same command (`curl … -d "done at $(date -u +%H:%M)"`, `curl …; date -u +%H:%M`): a `-u` or `--user` counts as a curl password only within that curl's own command (no `;`, `|`, `&`, newline or `$(` between the last `curl` and it), and never with a value starting with `+` or `%`. A curl password that follows such a character inside one of curl's own arguments (a quoted URL with `&` before `-u`, say) is no longer detected; `[sync] secret_keys` marks it. ([#134](https://github.com/luongnv89/mcc/issues/134))

## [0.11.0] - 2026-11-20

mcc now shows Devin beside your Claude Code accounts. `mcc devin` starts the Devin CLI with its own configuration and login, and once you are signed in to Devin, `mcc list`, `mcc` and `mcc usage` add a `devin` row with its daily and weekly quota and its overage balance. mcc never signs Devin in or writes its login, and asks Devin's API only with `[usage] live = true` (after a one-time note) or for `mcc usage --all`; otherwise it shows the last numbers it saw. `mcc usage` can now order its rows with `--sort` or the `usage.sort` setting, and by default lists accounts from least to most weekly usage, so the default profile's ★ row is no longer always first. The `mcc list` and `mcc usage` tables number their rows, and `--json` output gains a `provider` field.

### Added

- Devin as a provider beside your Claude Code accounts. `mcc devin [-- ARGS]` starts the Devin CLI as it is (`MCC_DEVIN_BIN`, else `PATH`, else `~/.local/bin/devin`): your arguments verbatim, no `--config`, no change to `HOME`, `XDG_*` or any other variable, so Devin uses its default configuration and its own login; `--dry-run` prints the command. mcc never signs Devin in and never writes its login (`$XDG_DATA_HOME/devin/credentials.toml`, else `~/.local/share/devin/credentials.toml`) or `~/.local/bin/devin`. When that login exists, `mcc list`, bare `mcc` and `mcc usage` add a `devin` row (`mcc usage devin` for Devin alone) with Devin's daily and weekly quota (never a 5-hour window) and its overage balance, read as custats-macos reads it: the session token goes to `https://app.devin.ai/api` (`/organizations`, then `/<org>/billing/quota/usage`). That lookup runs only with `[usage] live = true`, after a one-time note recorded as `[usage] devin_disclosed_at`, or for `mcc usage --all`, whose notice then names Devin's API; never with `MCC_NO_USAGE`, and never for bare `mcc`. Otherwise the last lookup's numbers are shown from `~/.mcc/providers/devin/quota.json`, which keeps the organization but never the token. `mcc doctor` checks Devin when its CLI or login is there (warnings at most). `devin` is now a reserved profile name (an existing profile of that name keeps working). ([#124](https://github.com/luongnv89/mcc/issues/124))
- `mcc list --json` and `mcc usage --json` (and `--json-v2`) objects end with a new `provider` field: `"claude"` for Claude Code profiles, `"devin"` for Devin's row, whose Claude Code counts are `null` and whose `usage` has `daily` and `overage_usd`. Schema 1 only gains fields; Claude Code profiles' `usage` objects are unchanged. ([#124](https://github.com/luongnv89/mcc/issues/124))
- The `mcc list` / bare `mcc` table and the `mcc usage` table number their rows (`#`), so the last number is how many accounts you have; Devin's row in `mcc usage` carries on from the profiles' numbers. The number sits one space before the name, so the tables keep the widths they fit before (bars at 80 columns in `mcc usage`, every column at 120 in `mcc list`).
- `mcc usage` orders its rows: `--sort` picks `name` (alphabetical), `five-hour` or `weekly` (percent used, least to most) or `five-hour-reset` / `weekly-reset` (soonest reset first) for one run, and `[usage] sort = "…"` (`mcc config set usage.sort ORDER`, `""` for the default) changes the order it uses with no `--sort`, which is now weekly usage least to most — the default profile's ★ row is no longer pinned first. A profile missing the order's value sorts last, and Devin's row is appended after the table. `mcc config get usage.sort` prints the order in effect. `--sort` rejects an unknown value, naming the valid ones. ([#126](https://github.com/luongnv89/mcc/issues/126))

### Fixed

- The `mcc-accounts` eval grader `evals/check_sandbox.py` no longer adds its own `claude` call to the output it grades. With mcc 0.10.0, the bare `mcc default` it ran for `global_default` asks `claude auth status`, which the sandbox's fake `claude` logged, so `claude_calls` gained a call the agent never made (one more per run), and `global_default` was always `default`, so "default unchanged" checks could not fail. It now reads the logs before running any mcc command, runs only `mcc project list`, and replaces `global_default` with `auth_changes` (the `claude auth login` and `auth logout` calls through which `mcc default` switches an account from 0.10.0) and `default_pointer` (the `default_profile` an mcc 0.7.0–0.9.x `mcc default PROFILE` wrote to `~/.mcc/config.toml`). `evals.json` grades "no account switched" from them. Eval tooling only: the shipped skill and mcc are unchanged. ([#122](https://github.com/luongnv89/mcc/issues/122))

## [0.10.0] - 2026-11-18

`mcc default` now changes the account of the default profile instead of pointing plain `claude` at another profile. `~/.claude` is always the default profile. `mcc default PROFILE` trades accounts with PROFILE: after you confirm, `~/.claude` signs out and in to PROFILE's account, and PROFILE signs out and in to the account `~/.claude` had. `mcc default --new` signs `~/.claude` in to another account and offers to keep the old one as a new profile. mcc only runs `claude auth logout` and `claude auth login`; it never reads, copies or moves a credential. The pointer an older `mcc default PROFILE` set up is removed on the next mcc command.

### Added

- `mcc here` shows which profile, and so which account, `mcc run` starts in the current directory, and why: `the default for DIR` (set on this folder with `mcc project set`), `inherited from parent folder DIR`, or `no project default here or in a parent folder` (the default profile, `~/.claude`). It prints the directory, the account (its organization; the email only with `[privacy] show_email`) and the profile's config directory, with a hint on how to change it. It resolves the profile through the same code as `mcc run` and the `mcc` status view, so they always agree. It is read-only, even before setup: no sign-in, no account switch, no lock, no first-run setup, no usage lookup, nothing written, not even a log line. Before mcc is set up it still answers (the default profile) and says mcc is not set up; a project default naming no profile is reported with a warning that `mcc run` stops there, and it still exits 0. ([#116](https://github.com/luongnv89/mcc/issues/116))

### Changed

- `mcc default PROFILE` trades accounts between `~/.claude` and PROFILE. mcc shows both accounts and asks first (`-y` confirms; without a terminal and without `-y` it exits 2). `~/.claude` signs out and in to PROFILE's account, then PROFILE signs out and in to the account `~/.claude` had. Each sign-in page is pre-filled with the account it expects (`--email`; a Claude Code without that option gets a warning and blank pages), and mcc checks that the sign-in landed on that account, in the same organization, before the next step. mcc runs `claude` for these steps without the credential variables (`ANTHROPIC_API_KEY`…), so it sees each profile's stored login. In a terminal a mismatch offers another try; otherwise mcc stops, prints the state it left, and the command that recovers it (`claude auth login --email ADDRESS` for `~/.claude`, `mcc exec PROFILE -- claude auth login --email ADDRESS` for the profile). A Ctrl+C during a sign-in stops the same way with exit 130. ([#115](https://github.com/luongnv89/mcc/issues/115))
- As soon as `~/.claude` is verified on PROFILE's account, mcc updates the registry, so a stop on PROFILE's side leaves it right: project defaults and allow lists that name `default` or PROFILE follow their account, so the two names trade places in them (asked before anything signs out; `-y` moves them, `--keep-projects` leaves them on their profile); PROFILE's recorded account, label and `share_cross_org_allowed_at` go, since they described the account it gave away; and both profiles' cached usage (`usage.json`) and failed-refresh mark (`refresh-failed-at`) in `~/.mcc/state/` are forgotten. Once PROFILE is verified, mcc records its new account under `[profiles.PROFILE.account]` and asks for a label (`--label LABEL` sets one, `-y` leaves none). Each profile keeps its history and sessions, so mcc warns before asking when the two accounts are not in the same organization: each can then resume what the other did there.
- `mcc default --new` signs `~/.claude` in to another account (`--email ADDRESS` pre-fills the sign-in page, `--sso` forces SSO). When no profile holds the account `~/.claude` is leaving, mcc first offers to keep it as a new profile: `mcc add ALIAS --clone`, signed in to that account, before `~/.claude` signs out. `--keep-as ALIAS` names it, and `-y` alone signs the account out of this machine. An `--email` that is a profile's account, or a sign-in that lands on one, is offered as a trade instead. Landing on the account `~/.claude` already had stops. A profile counts as holding an account only while it is signed in to it. A Console sign-in on `~/.claude` is signed out after a warning (no profile can keep it), and one Claude Code can't name is refused. `--email` needs a Claude Code whose `claude auth login` has it, and `--email`, `--sso` and `--keep-as` go with `--new` only (exit 2 otherwise).
- Refused before anything signs out: a profile that is signed out, or signed in to the same account as `~/.claude`; an Anthropic Console sign-in (API billing, which Claude Code keeps outside the profile's directory); a session-sharing profile that would share across organizations with the account it receives (stop sharing first with `mcc share PROFILE --off`); another mcc command refreshing either login. `mcc default` without arguments still prints `default` on stdout, and now says on stderr which account `~/.claude` is signed in to (the email only with `[privacy] show_email`) and which profiles share it; it asks `claude auth status` to find out.
- `~/.claude` is always the default profile: outside projects, `mcc run`, `mcc env` and the `mcc` status view always use it. `mcc list`, `mcc usage` and `mcc` always mark it with ★, and `is_global_default` in `--json` and `--json-v2` is `true` for `default` only. The hint `mcc add` prints when the default profile's account is already a profile's now names `mcc default --new` and `mcc default PROFILE`.
- Workspace defaults: a folder's default profile (`mcc project set`, with `--path` for any folder such as a workspace that holds several repositories) applies in every folder below it that has none of its own, up to `/`; with none, `~/.claude`. This was already how project defaults resolved; it is now documented, tested end to end, and visible: `mcc run`, `mcc env` and the `mcc` status view say `inherited from parent folder ~/work` when the default comes from a folder above the current one (`the default for ~/work` in that folder itself), and `no project default here or in a parent folder` instead of `no project default here`. ([#119](https://github.com/luongnv89/mcc/issues/119))

### Removed

- The pointer `mcc default PROFILE` kept from 0.7.0 to 0.9.x: `default_profile` in `~/.mcc/config.toml` and the `claude` function in the rc file between `# >>> mcc:default >>>` and `# <<< mcc:default <<<`. The next mcc command removes both, together, and says so once; plain `claude` (in new shells) and `mcc run` then start `~/.claude` again, and the profile still starts with its own command. `mcc doctor` reports a leftover pointer or rc block as a warning with `mcc default` as the fix. `mcc rename` and `mcc delete` no longer touch it, `mcc config set default_profile` explains that `~/.claude` is always the default, and `mcc default default` (or `claude`) now exits 2. **Upgrade note:** if you used `mcc default PROFILE` so that plain `claude` started PROFILE, plain `claude` and `mcc run` start `~/.claude` after the upgrade. To make PROFILE's account the default again, run `mcc default PROFILE` once: it now trades the accounts of `~/.claude` and PROFILE, and asks first. Or start PROFILE with its own command or `mcc run --profile PROFILE`. Scripts that read `is_global_default`, run `mcc default default` or `mcc config set default_profile`, or match `no project default here` on stderr (now `no project default here or in a parent folder`) need updating. ([#115](https://github.com/luongnv89/mcc/issues/115))

### Fixed

- `mcc add` no longer asks you to sign in again when you are already signed in to Claude Code. When `~/.claude` is missing, it used to create it and always run `claude auth login`, but on macOS the login lives in the Keychain and `~/.claude.json` sits outside `~/.claude`, so a missing `~/.claude` doesn't mean signed out: the new sign-in replaced the login you had and the account in `~/.claude.json`. `mcc add` now asks `claude auth status` first, without the credential variables (`ANTHROPIC_API_KEY`…) that would stand in for a stored login. Signed in: it keeps that login as the default profile's, skips the sign-in, and leaves `~/.claude.json` as it is (it only adds `hasCompletedOnboarding` when that is missing); `--email` and `--sso` go unused, with a warning that names `mcc default --new` for switching to another account on purpose. Signed out: it signs in as before. When `claude auth status` gives no answer mcc can read, it creates `~/.claude` without signing in, so it never replaces a login it can't see, and says to run `claude` or `mcc login default`. With `~/.claude` present, as before, setting up mcc and `mcc add ALIAS` never sign the default profile out or in. ([#118](https://github.com/luongnv89/mcc/issues/118))

## [0.9.0] - 2026-11-08

This release makes no change to the `mcc` binary apart from its version number. It adds [mcc-accounts](https://github.com/luongnv89/mcc/blob/v0.9.0/skills/mcc-accounts/SKILL.md), an agent skill that lets an AI agent use your profiles through mcc: tell which account a session or repository uses, report usage and login expiry, run a command or a headless `claude -p` task as a profile you name (`mcc exec`), and change mcc settings when you ask. It reads no tokens, hides emails, and never picks, ranks or runs an account because another one is at its limit. It works with mcc 0.7.0 and later.

### Added

- Per-profile settings overlays. A profile's `settings.json` is now the default's (paths rewritten) deep-merged with `[profiles.<alias>.settings]` in `~/.mcc/config.toml` and then `<profile>/settings.mcc.json`, so a profile can keep its own `model`, `env`, `permissions` or `statusLine`. Objects merge recursively, arrays and scalars replace the default's value whole, and `null` (JSON) removes a key. `add --clone` and every `sync` recompute the merge and record the merged result in `.mcc-sync.json`, so overlay keys never show up as local edits or conflicts in `sync`, `diff` or `list`, and changing the overlay is applied by the next sync (with the usual backup). Profiles with `settings` in `[sync] exclude` keep their own `settings.json` and the overlay is not applied (`sync` warns); an overlay `statusLine` takes precedence over the default's, the `mcc statusline` shim included. `sync.extra` entries naming `settings.mcc.json` are rejected. ([#45](https://github.com/luongnv89/mcc/issues/45))
- `mcc config get|set|edit|path` reads and changes `~/.mcc/config.toml` without hand-editing TOML. `set KEY VALUE` accepts `sync.exclude`, `sync.extra` (comma-separated, `""` for none), `privacy.show_email` (or its old name `usage.show_email`), `usage.live`, `launch.banner` (`true`/`false`), `profiles.ALIAS.label` and `profiles.ALIAS.color` (`""` removes either), checks the value as the command that uses it would, and saves through the comment-preserving, locked write; an invalid value is refused and the file is left unchanged. Keys other commands manage name that command instead. `get KEY` prints any key (dotted as in TOML; lists one item per line) and exits 1 when it isn't set. `edit` opens a copy in `$VISUAL`/`$EDITOR` and saves it only when it is valid mcc config (sync items, labels and `share_group` names included), offering to edit again otherwise. It holds no lock while the editor is open, and keeps your copy instead of saving when another command changed the file meanwhile. `path` prints the file's location. `get` and `path` never take the lock. ([#48](https://github.com/luongnv89/mcc/issues/48))
- `mcc env [PROFILE]` prints the shell line that points `CLAUDE_CONFIG_DIR` at the profile `mcc run` would start in the current directory (the project's default, else the default profile, which prints `unset CLAUDE_CONFIG_DIR`), or at PROFILE. It prints the fish form (`set -gx`) for fish, chosen with `--shell` or from `$SHELL`, and the bash form inside a direnv `.envrc`; paths are single-quoted, so spaces and quotes are safe. With `eval "$(mcc env)"` in a project's `.envrc`, plain `claude`, IDE extensions and scripts use the project's profile; the README documents the direnv setup. ([#42](https://github.com/luongnv89/mcc/issues/42))
- `mcc exec PROFILE -- CMD...` runs any command with a profile's `CLAUDE_CONFIG_DIR` and exits with its status, e.g. `mcc exec work -- claude mcp list`. `mcc exec --all -- CMD...` runs it once per profile, the default first, prints each profile's exit status, and exits 0 only when it succeeded everywhere (else with the first failing status). A command that can't be found counts as exit 127 (126 when it can't be run), and Ctrl+C stops at the current profile. Neither command takes mcc's config lock, so the command may run mcc itself. `env` and `exec` are reserved and can't be used as aliases. ([#43](https://github.com/luongnv89/mcc/issues/43))
- Versioned JSON output. `mcc list`, `mcc usage` and `mcc project list` take `--json-v2`, which prints `{"schema": 2, "profiles": [...]}` (`"projects"` for `mcc project list`) around the same objects as `--json`, so scripts can check the schema version before reading. `--json` is unchanged: still a bare array (schema 1, implicit), so `jq '.[]'` scripts keep working; within a schema, fields are only ever added. The README's *JSON output and its schema version* section documents both shapes and the deprecation path. ([#49](https://github.com/luongnv89/mcc/issues/49))
- Session-sharing groups and a cross-organization guard. `mcc share ALIAS --group NAME` shares only with the profiles of group NAME, through a store of its own (`~/.mcc/shared/groups/NAME/projects`), recorded as `share_group`; without `--group`, the profile's recorded group (else the `default` group, `~/.mcc/shared/projects`) is used, and moving to another group needs `--off` first. Joining a group whose profiles are in another organization, or whose account mcc can't identify, is refused unless `--allow-cross-org` is passed (recorded as `share_cross_org_allowed_at`, cleared by `--off`); organization ↔ personal is the strictest case and also needs a confirmation in a terminal. `mcc list` shows `(shared: NAME)` and `share_group` in `--json`. **Upgrade note:** profiles that already share keep `~/.mcc/shared/projects` as the `default` group's store, with nothing moved; a group that mixes organizations gets a warning, never a refusal. ([#40](https://github.com/luongnv89/mcc/issues/40))
- `mcc sync` is three-way. `add --clone` and `sync` record what they wrote in `<profile>/.mcc-sync.json` (a hash per path and MCP server), and the next sync compares the default, the profile and that record: a path changed only in the default is updated, one edited or deleted only in the profile is kept and reported as a local edit, and one changed in both (or added on both sides) is a conflict, kept unless `--force` (which backs it up to `.mcc-backup/` first, like every overwrite). `--dry-run` shows the classification and writes nothing, the record included. A profile without a record (or with one that can't be read) is compared two-way once, and that sync, `--dry-run` included, first warns with each path and MCP server it replaces and where they are backed up, even with `--quiet` ([#87](https://github.com/luongnv89/mcc/issues/87)). `mcc diff ALIAS [--only ITEMS]` lists each differing path with its class and a line diff, and `mcc list` has a `SYNC` column (`✓`, `3 behind`, `2 local edits`, `1 conflict`; `sync` in `--json`, a `Sync` row in `--long`). `sync.extra` entries naming `.mcc-sync.json` are rejected. ([#41](https://github.com/luongnv89/mcc/issues/41))
- `mcc add` records the account a profile logs in to under `[profiles.<alias>.account]` in `~/.mcc/config.toml` (email, account UUID, organization name and UUID, as Claude Code reports them), warns when another profile, the default included, is already logged in to the same account, and asks for an optional label (`personal`, the account's organization, or any text), kept as `label`. `--label LABEL` sets it without asking. `mcc list` shows the organization (in `ACCOUNT` when the profile has no label, and in `--long`), `--long` cards add `Organization ID` and `Label` rows, and `--json` adds `organization_uuid` and `label` per profile; `organization` (and `account`) fall back to the recorded account when the profile's `.claude.json` has none. ([#39](https://github.com/luongnv89/mcc/issues/39))
- Per-project profiles. `mcc project set PROFILE` makes PROFILE the one `mcc run` starts in the current git repository (or directory, or `--path DIR`). `--allow NAME` (repeatable or comma-separated) names the other profiles `mcc run` may offer when PROFILE is at its limit; setting the project again without it clears the list. `mcc project unset` and `mcc project list [--json]` manage them. They are kept as `[projects."<dir>"]` tables in `~/.mcc/config.toml`. `mcc rename` updates them, and `mcc delete` removes the ones naming the deleted profile and takes it off the allow lists.
- `mcc run [-- CLAUDE_ARGS]` starts Claude Code with the current project's default profile, or the default profile outside every project. mcc never switches accounts on its own. When that profile is at its 5-hour or weekly limit, `mcc run` asks what to do: waiting (starting nothing) is the default, starting it anyway comes next, and other profiles are offered only when the project allows them, by name and without their usage. Only that profile's usage is fetched. Without a terminal it stops (exit 2). `--profile NAME` starts NAME without checking usage. Starting a profile other than the project's, from the prompt or with `--profile`, prints a terms-of-service note on stderr. `--dry-run` prints the profile it would start. If the profile's usage can't be read, it starts. ([#31](https://github.com/luongnv89/mcc/issues/31))
- `mcc list` shows the project defaults under the profile table (project, profile and account, with `← here` for the current directory). `--long` cards have a `Default for` row, and `--json` has a `project_defaults` array per profile.
- `project` and `run` are reserved and can't be used as aliases.
- Opt-in `mcc statusline`, a Claude Code status-line shim. `mcc statusline install` backs up `~/.claude/settings.json` to `~/.mcc/backups/`, records the current `statusLine` and sets `mcc statusline` in its place (never twice); `--prefix` starts the status line with the active profile's name, e.g. `[work]`. On every refresh the shim works out the profile from `CLAUDE_CONFIG_DIR`, saves the session's `rate_limits` (5-hour and weekly `used_percentage` and `resets_at`) to `~/.mcc/state/<profile>/usage.json`, runs the previous `statusLine` command with the same stdin and prints its output, without taking mcc's lock or writing `~/.mcc/config.toml`. Profiles get it with their next `mcc sync`; when `[sync] exclude` has `settings`, `install` offers to add it to each profile directly (`--yes` accepts). `mcc statusline uninstall` restores the previous `statusLine` everywhere. `mcc rename` and `mcc delete` move or remove the profile's state, and `statusline` is reserved as an alias. ([#33](https://github.com/luongnv89/mcc/issues/33))
- A GitHub Actions CI workflow runs `cargo test` on Linux and macOS, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `shellcheck install.sh` and `brew audit` on the Homebrew formula for every push and pull request. ([#32](https://github.com/luongnv89/mcc/issues/32))

### Changed

- `mcc list` hides account emails by default, like `mcc usage`: the table, `--long`, and `account` in `--json` / `--json-v2` (`null`, as are an `organization` and `label` that contain an email; no field is removed). `--show-email` / `--hide-email` override it for one run. The setting moved to `[privacy] show_email` (`mcc config set privacy.show_email true`) and applies to both commands; `[usage] show_email` and `usage.show_email` still work, and a `true` there moves to `[privacy]` the next time mcc saves the config ([#57](https://github.com/luongnv89/mcc/issues/57)).
- The default `mcc list` table fits 120 columns: `NAME`, `ACCOUNT` (the label, else the organization, after the email when emails are shown; long cells are cut with `…`), `5H`, `WEEK`, `LAST USED` and `SYNC`. The command, organization, skill/agent/command/plugin/MCP/hook counts, size, last sync and usage age moved to `mcc list --long`; JSON is unchanged ([#56](https://github.com/luongnv89/mcc/issues/56)).
- Internal: the opt-in live usage request (`[usage] live = true`) uses `ureq` 3 instead of 2, still on rustls with the bundled webpki roots (no native-tls or OpenSSL), and no new minimum Rust version (`ureq` 3 needs 1.85; mcc stays at 1.88). The request behaves as before: 2 s to connect, 4 s in all, no redirects followed (so the bearer token is never sent elsewhere), the `mcc/<version>` User-Agent, and 401, 403, 429 and other statuses reported as before. `ureq` 3 would read `HTTPS_PROXY` and similar variables by default, so mcc turns that off to keep sending the token straight to the endpoint, as `ureq` 2 did. Tests against a local HTTP server check each of these. ([#52](https://github.com/luongnv89/mcc/issues/52))
- `mcc add --clone` shares the default's plugins instead of copying `plugins/cache` and `plugins/marketplaces` into the new profile (see *Shared plugins* above); `--copy-plugins` keeps the old full copy, and so does `[sync] exclude` with `plugins` (nothing plugin-related is copied or shared then). **Upgrade note:** existing profiles are unchanged and keep their copy until `mcc link ALIAS plugins`. ([#47](https://github.com/luongnv89/mcc/issues/47))
- Internal: `mcc add`, `mcc rename`, `mcc refresh-launchers` and `mcc share` undo a failed run through one shared rollback helper (`src/txn.rs`) instead of four copies. Rollback order, messages and what is undone are unchanged. ([#50](https://github.com/luongnv89/mcc/issues/50))
- `mcc list`, `mcc usage` and `mcc run` read usage from the rate limits `mcc statusline` caches in `~/.mcc/state/<profile>/usage.json`, and no longer read any login by default. They show how old the numbers are (an `UPDATED` column, `Usage updated` in `mcc list --long`, `· 12m ago` in `mcc run`), treat a cached window whose reset time has passed as obsolete, and show `—` with a hint to run `/usage` in Claude Code for a profile with nothing current cached (`reason: "no_data"` in `--json`). The `usage` JSON object gains `source` (`cache` or `live`) and `updated_at`. **Upgrade note:** the live lookup, which reads each profile's OAuth token (from `.credentials.json` or the macOS Keychain) and calls Anthropic's undocumented usage endpoint, is now opt-in with `live = true` under `[usage]` in `~/.mcc/config.toml`; the first command that uses it prints a one-time disclosure, recorded as `live_disclosed_at`. `docs/privacy.html` describes the change. ([#34](https://github.com/luongnv89/mcc/issues/34))
- The session-sharing and `mcc run` terms-of-service notes, the README and the docs site now mention the updated Anthropic Usage Policy that takes effect November 12, 2026. The README and docs site quote the Team and Enterprise seat rules separately, each in its own words, document `MCC_NON_INTERACTIVE`, and `docs/PLAN.md` is marked as a historical plan. ([#38](https://github.com/luongnv89/mcc/issues/38))
- The full session-sharing note is printed only the first time sharing is turned on for a profile, and when is recorded as `share_note_acknowledged_at` under `[profiles.ALIAS]` in `~/.mcc/config.toml`. Later `mcc share` and `ALIAS --mcc-share` runs print a one-line reminder instead. ([#36](https://github.com/luongnv89/mcc/issues/36))

### Fixed

- `~/.mcc/logs/mcc.log` no longer grows without bound: once it reaches about 1 MB it is moved to `mcc.log.1` (replacing the previous one) before the next line is written, so at most about 2 MB of log, which can include account emails, is kept. A failed rotation never breaks a command. ([#51](https://github.com/luongnv89/mcc/issues/51))
- `mcc add` no longer warns about a duplicate account (and suggests `mcc delete`) when the same login is used in another organization, such as a personal plan and a work seat: those have usage limits of their own, so it prints a note instead. The warning stays for the same login in the same organization. ([#40](https://github.com/luongnv89/mcc/issues/40))
- The Keychain login lookup (live usage) no longer needs `USER`: when it is unset, as under launchd, cron or some IDE tasks, the account name comes from the password database (`getpwuid_r`) or `id -un`, so a logged-in profile is no longer reported as `not_logged_in`. ([#37](https://github.com/luongnv89/mcc/issues/37))
- Saving `~/.mcc/config.toml` keeps hand-written comments and formatting, and a command that changes nothing (such as `ALIAS --mcc-share` on a profile that already shares) no longer rewrites it. Every command that writes the config holds an advisory lock on `~/.mcc/.lock` from loading it to saving it, so concurrent runs no longer lose each other's changes; a command that has to wait says so. ([#35](https://github.com/luongnv89/mcc/issues/35))
- The `mcc project` and `mcc list` tests expected absolute project paths, but mcc shows a project under `$HOME` as `~/…`; they now expect what mcc prints, so they pass on Linux as well as macOS. ([#32](https://github.com/luongnv89/mcc/issues/32))
- `mcc sync` backs up every file or folder it overwrites or removes (such as `CLAUDE.md`, skills and agents) to `<profile>/.mcc-backup/<timestamp>/`, not only `settings.json`, `settings.local.json` and `.claude.json`, so edits made in a profile can be restored. A symlink is backed up as the link itself. `sync.extra` entries that are empty, `.` or inside `.mcc-backup` are rejected. ([#30](https://github.com/luongnv89/mcc/issues/30))
- A `link` entry under `[profiles.ALIAS]` in `~/.mcc/config.toml` that can't be linked, such as a hand-written `link = ["settings"]` (or `hooks`, or an unknown item), no longer makes `mcc sync`, `mcc diff` and the `mcc list` SYNC column skip that item and report the profile as in sync. The entry is ignored, with one warning per run that names the profile and the entry and says to remove it with `mcc config edit`, and the item is synced and compared like any copied item. The entry itself is left in the config. ([#86](https://github.com/luongnv89/mcc/issues/86))
- The address given to `mcc add --email` no longer appears in `~/.mcc/logs/mcc.log`: the command line logged for each run has `<redacted>` in place of the value of `--email ADDRESS` or `--email=ADDRESS`, a value mcc then refuses included. After the login, the signed-in account's email, usually the same address, is still shown and logged as for any profile. ([#88](https://github.com/luongnv89/mcc/issues/88))

### Security

- The install script downloads release files over HTTPS only, redirects included, and builds from a local clone only when it runs as that clone's `install.sh`. Piped to `sh` (`curl … | sh`), earlier versions took the current directory for a clone and built and installed it whenever its `Cargo.toml` had `name = "mcc"`. ([#53](https://github.com/luongnv89/mcc/issues/53))

## [0.3.0] - 2026-10-13

Profiles can now opt in to session sharing with `mcc share ALIAS` or `ALIAS --mcc-share`, so `--resume` lists the sessions of every sharing profile, and `mcc refresh-launchers` updates launchers and shell aliases made by an older mcc.

### Added

- Opt-in session sharing between profiles, off by default. `mcc share ALIAS` (or starting a profile with `ALIAS --mcc-share`) links the profile's `projects/` to `~/.mcc/shared/projects`, so `--resume` lists the sessions of every sharing profile. `mcc share ALIAS --off` gives the profile its own copy again. The setting is `share_sessions` under `[profiles.ALIAS]` in `~/.mcc/config.toml`. Only sessions are shared: never credentials, the account, history or live session state. Every time sharing is turned on, mcc prints a note about Anthropic's Consumer Terms and Usage Policy. `mcc list` marks sharing profiles, and `--json` has `share_sessions` and `launcher_current`. ([#25](https://github.com/luongnv89/mcc/issues/25), [#26](https://github.com/luongnv89/mcc/pull/26))
- `mcc refresh-launchers [ALIAS...]` rewrites launchers and shell aliases from the current templates. ([#25](https://github.com/luongnv89/mcc/issues/25), [#26](https://github.com/luongnv89/mcc/pull/26))

### Changed

- New launchers handle `--mcc-share`, and new shell aliases run the launcher instead of calling `claude` directly. `CLAUDE_CONFIG_DIR` is unchanged, so logins are kept. **Upgrade note:** existing launchers and aliases are not modified; run `mcc refresh-launchers` once to use `ALIAS --mcc-share` with profiles created before this release. ([#25](https://github.com/luongnv89/mcc/issues/25), [#26](https://github.com/luongnv89/mcc/pull/26))
- `mcc list` prints a hint to run `mcc refresh-launchers` while a launcher predates session sharing. ([#25](https://github.com/luongnv89/mcc/issues/25), [#26](https://github.com/luongnv89/mcc/pull/26))
- `share` and `refresh-launchers` are reserved and can't be used as aliases. ([#25](https://github.com/luongnv89/mcc/issues/25), [#26](https://github.com/luongnv89/mcc/pull/26))

## [0.2.0] - 2026-10-13

`mcc usage` is now a compact table that hides account emails by default, and `mcc rename` renames a profile and its command while keeping its login.

### Added

- `mcc rename ALIAS NEW` (alias `mv`): renames a profile and its command. It installs the new launcher and alias block, renames the registry entry, then removes the old launcher and alias. The new name is checked like an alias in `mcc add`, and a failure rolls the changes back. The profile directory, and so its login, is kept. ([#24](https://github.com/luongnv89/mcc/issues/24), [#23](https://github.com/luongnv89/mcc/pull/23))
- `[usage] show_email` in `~/.mcc/config.toml`, plus `--show-email` / `--hide-email` on `mcc usage`, to choose whether account emails are shown. ([#24](https://github.com/luongnv89/mcc/issues/24), [#23](https://github.com/luongnv89/mcc/pull/23))

### Changed

- `mcc usage` shows a compact table, one row per profile, instead of a block per profile: `PROFILE`, then the bar and percent used, time until reset and reset time for the 5-hour and weekly windows. On narrow terminals the reset time goes first, then bars shrink 10 → 5 → 0. ([#24](https://github.com/luongnv89/mcc/issues/24), [#23](https://github.com/luongnv89/mcc/pull/23))
- `mcc usage` hides account emails by default, in the table and in `--json` (`account` is `null`). Use `--show-email` or `[usage] show_email = true` to show them. ([#24](https://github.com/luongnv89/mcc/issues/24), [#23](https://github.com/luongnv89/mcc/pull/23))
- `mcc add <old name>` names the renamed profile that still uses that name's directory, instead of only saying that the directory exists. ([#24](https://github.com/luongnv89/mcc/issues/24), [#23](https://github.com/luongnv89/mcc/pull/23))

### Fixed

- `mcc delete <old name>` refuses to delete a directory that a renamed profile still uses. ([#24](https://github.com/luongnv89/mcc/issues/24), [#23](https://github.com/luongnv89/mcc/pull/23))

## [0.1.0] - 2026-10-10

The first version of mcc.

### Added

- Homebrew formula for macOS and Linux: `brew install luongnv89/tap/mcc` builds mcc from source and installs bash, zsh and fish completions. `brew upgrade mcc` and `brew uninstall mcc` work as usual. The formula lives in `packaging/homebrew/mcc.rb`. ([#14](https://github.com/luongnv89/mcc/issues/14))
- `mcc usage [PROFILE] [--json]`: every profile's 5-hour and weekly usage in detail, with a bar, percent used and left, time until reset, and the reset time in local time. `default` or `claude` selects `~/.claude`; an unknown name exits 2. ([#16](https://github.com/luongnv89/mcc/issues/16), [#20](https://github.com/luongnv89/mcc/pull/20))
- Usage meters in `mcc list`: a coloured bar (green, yellow at 80%+, red at 95%+) and colour-independent `!` / `!!` markers, sized to the terminal width. ([#17](https://github.com/luongnv89/mcc/issues/17), [#20](https://github.com/luongnv89/mcc/pull/20))
- 5-hour and weekly usage in `mcc list`: new `5H` and `WEEK` columns, lines in `--long` cards, and a `usage` object in `--json`, for every profile including the default. Each profile's own login is used; failures show `unavailable` with a reason and never change the exit status. ([#13](https://github.com/luongnv89/mcc/issues/13), [#15](https://github.com/luongnv89/mcc/pull/15))
- `--no-usage` and `MCC_NO_USAGE` to skip the usage fetch, and the `MCC_USAGE_URL` / `MCC_SECURITY_BIN` test overrides. ([#15](https://github.com/luongnv89/mcc/pull/15))
- `mcc completions` for bash, zsh, fish, elvish and PowerShell, plus `install.sh`. ([#12](https://github.com/luongnv89/mcc/pull/12))
- `mcc list` (table, `--long` cards, `--json`), `mcc sync` (plan, backup, apply; `--dry-run`, `--prune`, `--only`, `--all`) and `mcc delete` (type-to-confirm or `--yes`, logout, removes only what mcc created). ([#12](https://github.com/luongnv89/mcc/pull/12))
- `mcc init` (OS, terminal, shell, rc file and `claude` detection, run automatically on first use) and `mcc add` (alias validation, clone with path rewriting, launcher, managed rc block, login, rollback on failure). ([#12](https://github.com/luongnv89/mcc/pull/12))
- Apache-2.0 license, contributing guide, code of conduct, security policy, and issue and pull request templates. ([#18](https://github.com/luongnv89/mcc/issues/18), [#19](https://github.com/luongnv89/mcc/pull/19))

### Fixed

- `mcc usage` keeps the full 20-cell bar at 80 columns: it drops the absolute reset time before shrinking the bar, and shrinks in the same 20/10/0 steps as `mcc list --long`. ([#21](https://github.com/luongnv89/mcc/pull/21))
- Relative symlinks (such as `skills/x -> ../../.agents/skills/x`) are re-resolved from their source location, so cloned profiles don't get broken links. ([#12](https://github.com/luongnv89/mcc/pull/12))

### Security

- Access tokens are kept in memory only, sent only to the usage endpoint for their own profile, and never printed, logged or written to disk. Expired tokens are never sent. ([#15](https://github.com/luongnv89/mcc/pull/15))
- GitHub private vulnerability reporting is enabled, and `contact@luongnv.com` is listed as the security contact. ([#21](https://github.com/luongnv89/mcc/pull/21))
